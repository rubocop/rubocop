= Auto-generating Configuration

If you have a code base with an overwhelming amount of offenses, it can
be a good idea to use `rubocop --auto-gen-config`, which creates
`.rubocop_todo.yml` and adds `inherit_from: .rubocop_todo.yml` in your
`.rubocop.yml`. By default, the generated file contains
configuration to silence offenses by changing cop settings, excluding
offending files, or disabling a cop when its file limit is
reached. This is the `--auto-gen-config` behavior.

To generate per-file offense allowances in place of `Exclude` lists,
add the `--auto-gen-allowed-offenses` option. For example:

[source,console]
----
$ rubocop --auto-gen-config --auto-gen-allowed-offenses
----

The generated `AllowedOffenses` maps record the offense count for each cop in
each inspected file. Offenses remain suppressed while a file stays within its
count; if a file exceeds its count, the run reports that file's offenses for
the cop. Files absent from the map have an allowance of zero, so partial runs
honor the same per-file baseline as full-project runs. Run the command over the
full project for a complete baseline; if file paths are passed, only those
files are included. The option is recorded in the generated TODO file so
`--regenerate-todo` preserves it. See
xref:configuration/cop_settings.adoc#allowedoffenses[AllowedOffenses] for
details.

Per-file maps are subject to `--exclude-limit` (15 files by default). If a cop
has offenses in more files than the limit, RuboCop follows the default
`--auto-gen-config` fallback for that cop: adjusting `Max` when possible or
disabling the cop. Use `--no-exclude-limit` to generate maps with any number
of files.

`AllowedOffenses` now requires a file-to-count map; the previous integer form
is no longer accepted. Regenerate an existing TODO file with
`--auto-gen-allowed-offenses` after upgrading. This option cannot be combined
with `--auto-gen-only-exclude`.

By default, `--exclude-limit COUNT` controls how many files are excluded
before a cop is disabled or a `Max` value is adjusted, and how many files can
be included in a per-file allowance map. For example,
`rubocop --auto-gen-config --exclude-limit 5` sets the limit to 5; the default
is 15. Use `--no-exclude-limit` to avoid applying those limits.

== Working through the TODO

The next step is to cut and paste configuration from `.rubocop_todo.yml`
into `.rubocop.yml` for everything that you think is in line with your
(organization's) code style and not a good fit for a todo list.

TIP: Pay attention to the comments above each entry in `.rubocop_todo.yml`.
They can reveal configuration parameters such as `EnforcedStyle`, which can
be used to modify the behavior of a cop instead of disabling it completely.

Then you can start removing the entries in the generated
`.rubocop_todo.yml` file one by one as you work through all the offenses
in the code. You can also regenerate your `.rubocop_todo.yml` using
the same options by running `rubocop --regenerate-todo`.

[[keeping-the-todo-from-rotting]]
== Keeping the TODO from rotting

Entries in `.rubocop_todo.yml` outlive their purpose silently: when an
excluded file is fixed as a side effect of other work, or deleted, nothing
tells you the entry is no longer needed. Running with
`--report-unused-todo-entries` reports every `Exclude` entry whose cop no
longer flags its file and fails the run when any are found:

[source,console]
----
$ rubocop --report-unused-todo-entries

1 unused todo entry found in `.rubocop_todo.yml`:
  Style/ClassVars: lib/fixed_file.rb
----

A glob entry is judged against its matching source files, not as a literal
path, and is kept when any of those files still trigger that cop.

Regenerating the todo also removes stale entries, but the two commands
serve opposite purposes. Regeneration re-baselines: it rewrites the whole
file, and in doing so also *absorbs any new offenses* into the todo list -
run in CI, it would legitimize every newly introduced offense.
`--report-unused-todo-entries` only ever moves in one direction: new
offenses still fail the build as usual, and stale entries fail it too until
they are removed. That makes it safe to run on every CI build as a ratchet
that forces the todo list to shrink over time, while `--regenerate-todo`
remains a deliberate, local re-baselining step.

Entries for cops that are not loaded in the current run (for example,
extension cops when running plain `rubocop`) are not judged, since the
absence of their offenses proves nothing.

Another way of silencing offense reports, aside from configuration, is
through xref:usage/source_code_directives.adoc[source code directives]. These can be added manually or
automatically.

== Metrics cops

By default, Metrics cops get `Max` parameters that prevent offenses the next
time you run `rubocop`. The `--auto-gen-only-exclude` option prefers `Exclude`
entries instead, adjusting `Max` only when the number of files with offenses is
greater than the `--exclude-limit`. `--auto-gen-allowed-offenses` preserves
threshold settings such as `Max` and generates per-file allowances in place of
`Exclude` entries when no threshold setting can be generated.

== EnforcedStyle

Some cops have a configurable option named `EnforcedStyle`.
By default, when generating the `.rubocop_todo.yml`, if one style is used
for all files, these cops will add the settings for the style being used.
If you want to exclude on a file-by-file basis,
add the `--no-auto-gen-enforced-style` option along with `--auto-gen-config`.
